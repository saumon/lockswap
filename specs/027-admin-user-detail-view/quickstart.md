# Quickstart: Admin User Detail View

**Feature**: [../spec.md](../spec.md) | **Branch**: `027-admin-user-detail-view`

A runnable validation guide proving the feature end-to-end, once implemented. Not a test suite — see
`tasks.md` (generated by `/speckit-tasks`) for the actual automated coverage. Field/route/DOM details
referenced below are fixed in `contracts/admin-user-detail.md` and `data-model.md`; this guide does not
repeat them.

## Prerequisites

- `bin/rails db:prepare` (applies the new migration).
- Fixture users already in `test/fixtures/users.yml`: `frank` (admin), `bob` (floor "3", locker
  "B12"), `carol` (floor "2", no locker). Fixture proposals in
  `test/fixtures/locker_swap_proposals.yml`: `alice_pending_to_bob` (pending),
  `dave_declined_to_carol` (declined). These already cover "has a floor and locker," "pending
  proposal," and "declined proposal with a comment" without creating new records.
- For manual exploration rather than the fixture-backed test suite: `bin/rails server`, sign in as
  `frank@example.com` / `password123` (see `test/fixtures/users.yml`'s comment on the shared fixture
  password).

## Scenario 1 — Reach the detail screen, and only as an admin (User Story 1)

1. Sign in as `frank` (admin), visit `/admin/users`.
2. Click `bob`'s email in the list.
3. **Expect**: landed on `/admin/users/<bob's id>`, showing `bob`'s own information, not any other
   account's.
4. Sign out, sign in as `bob` (standard account), request `/admin/users/<carol's id>` directly.
5. **Expect**: redirected away with the "administrators only" message (`application.administrators_only`
   — unchanged, 013), no account information shown.
6. Sign out entirely, request the same address.
7. **Expect**: redirected to sign in.

## Scenario 2 — Full profile, search status and proposal history (User Story 2)

1. As `frank`, open `bob`'s detail screen.
2. **Expect**: email, role, registration date, floor "3", locker "B12" all shown, matching
   `/admin/users` and `bob`'s own homepage.
3. **Expect**: search status shows `bob` has neither a standing wish nor an active proposal (no
   `locker_wishes` fixture ties one to `bob`, and `alice_pending_to_bob` names `bob` as recipient — a
   *pending* proposal — so `bob` **does** show one active proposal here; pick a genuinely
   wish-and-proposal-free fixture, or read carefully: this step should actually show `bob`'s one active
   (pending) proposal, not "neither." Use `carol` instead for the "neither" case if a wish-free,
   proposal-free account is needed for that specific assertion.)
4. Open `dave`'s detail screen instead (or add a fixture wish for one of these accounts if none
   currently combines "has a wish" with "has full proposal history" cleanly).
5. **Expect**: the proposal-history section lists both `dave`'s fixture proposals
   (`dave_declined_to_carol`, sent; and any other fixture involving `dave`), each showing direction,
   counterparty, date, status, and — for the declined one — its comment ("Found another swap").
6. Open an account with no fixture proposals at all.
7. **Expect**: the history section states plainly there are none, rather than an empty table.

## Scenario 3 — Edit floor/locker on a user's behalf (User Story 3)

1. As `frank`, open `carol`'s detail screen (floor "2", no locker).
2. Activate the pencil icon.
3. **Expect**: an editable form appears, pre-filled with floor "2" and an empty locker field.
4. Submit locker number `"B12"` (already `bob`'s, same floor `bob` is *not* on — pick a locker actually
   taken on floor "2" to exercise the uniqueness refusal, or use a value genuinely free to exercise the
   success path first).
5. **Expect** (uniqueness conflict): refused with the same message a self-service conflicting edit
   shows (`user.messages.locker_number_taken`); no data changed.
6. Submit a free locker number instead.
7. **Expect**: `carol`'s detail screen now shows the new locker number, and a provenance line naming
   `frank` and the current time.
8. Build a pending proposal touching `carol` (e.g. reuse `dave_declined_to_carol`'s shape but with a
   `pending` status fixture, or create one via the app), then attempt to edit `carol`'s floor/locker
   again.
9. **Expect**: refused with the same "cannot be changed while ... an active swap proposal" message the
   account holder would see attempting the same edit (Clarifications: no admin bypass).

## Scenario 4 — Cancel a user's search on their behalf (User Story 4)

1. Give `bob` a standing wish (e.g. via the app, or a new fixture).
2. As `frank`, open `bob`'s detail screen.
3. **Expect**: a "cancel search" button is visible.
4. Click it, dismiss the confirmation dialog instead of confirming.
5. **Expect**: the wish is untouched.
6. Click it again, confirm this time.
7. **Expect**: the wish is gone from this screen, from `bob`'s own homepage, and from `/locker_wishes`;
   a provenance line on the detail screen names `frank` and the current time.
8. Open an account with no standing wish.
9. **Expect**: no cancel-search button is shown.

## Scenario 5 — Accessibility

1. Run the project's existing axe-core audit helper against `/admin/users/<any id>` (same helper other
   system tests already call — see `test/system/` for the existing pattern).
2. **Expect**: no new violations; the pencil icon and the cancel-search button both have accessible
   names (FR-012), reachable and operable via keyboard alone.
