# Quickstart: Admin Rights Controls on the User Detail Screen

**Feature**: [../spec.md](../spec.md) | **Branch**: `028-move-admin-grant-button`

A runnable validation guide proving the feature end-to-end, once implemented. Not a test suite — see
`tasks.md` (generated by `/speckit-tasks`) for the actual automated coverage. Route/DOM/copy details
referenced below are fixed in `contracts/admin-user-rights-controls.md` and `data-model.md`; this guide
does not repeat them.

## Prerequisites

- No migration to apply (data-model.md: none).
- Fixture users already in `test/fixtures/users.yml`: `frank` (bootstrap admin), `grace` (granted
  admin — `admin_granted_by: frank`), `carol` (standard).
- `bin/rails server`, sign in as `frank@example.com` / `password123` (see `test/fixtures/users.yml`'s
  comment on the shared fixture password) for manual exploration.
- `bin/rails tailwindcss:build` after any stylesheet touch (none expected — this feature reuses the
  existing `.btn`/`.btn-secondary`/`.btn-sm` vocabulary, per research.md R5).

## Scenario 1 — Grant, relocated (User Story 1)

1. Sign in as `frank`, visit `/admin/users`.
2. **Expect**: no row has a "Grant admin rights" (or any) control in its last column, and the table has
   no "Actions" column header at all.
3. Click `carol`'s email to reach her detail screen.
4. **Expect**: a "Grant admin rights" control is present.
5. Activate it.
6. **Expect**: a confirmation naming `carol`'s email appears, stating she will gain administrator
   rights — with no claim that this cannot be undone.
7. Confirm.
8. **Expect**: `carol`'s detail screen now shows her as an administrator, with "Granted by
   frank@example.com on <today>" beneath the badge; back on `/admin/users`, her row shows the same
   badge.

## Scenario 2 — Revoke (User Story 2)

1. As `frank`, open `grace`'s detail screen (already an administrator, granted by `frank` per
   fixtures).
2. **Expect**: a "Revoke admin rights" control is present (distinct from the grant control, which is
   not shown since `grace` is already an administrator).
3. Activate it, then dismiss the confirmation instead of accepting.
4. **Expect**: `grace` is still an administrator; nothing changed.
5. Activate it again, confirm this time.
6. **Expect**: `grace`'s detail screen now shows her as a standard account, with no grant-provenance
   line at all (not "revoked by...", nothing — FR-018); back on `/admin/users`, her row shows the same.
7. Open `grace`'s detail screen again and grant her rights again.
8. **Expect**: she is an administrator again, with a fresh "Granted by frank@example.com on <today>"
   line — no trace of the earlier grant/revoke cycle.

## Scenario 3 — Cannot revoke your own rights (User Story 3)

1. As `frank`, open your own detail screen (`/admin/users/<frank's id>`).
2. **Expect**: no "Revoke admin rights" control is present, even though the account is an
   administrator.
3. Using a request tool (e.g. `curl` with `frank`'s session cookie, or a controller test), send
   `PATCH /admin/users/<frank's id>/revoke_admin` directly.
4. **Expect**: refused; `frank` is still an administrator; an alert explains why.
5. Repeat step 3 signed in as `grace` (a second administrator) targeting `grace`'s own id instead.
6. **Expect**: same refusal — the rule applies to whichever administrator is acting, not to `frank`
   specifically.

## Scenario 4 — Non-administrators are refused either action

1. Signed out, `PATCH` either `/admin/users/<carol's id>/grant_admin` or
   `/admin/users/<grace's id>/revoke_admin` directly.
2. **Expect**: redirected to sign in; no account's rights change.
3. Signed in as `carol` (standard account), repeat both requests, targeting any other account.
4. **Expect**: both refused with the site's existing "administrators only" message; no account's
   rights change.

## Scenario 5 — Vanished account mid-flight

1. As `frank`, open a standard account's detail screen in one tab.
2. In another context, delete that account (e.g. via its own "Cancel my account").
3. Back in the first tab, activate and confirm the grant control.
4. **Expect**: told plainly the account no longer exists; landed back on `/admin/users` (not a broken
   detail page for an id that no longer resolves).
5. Repeat with an administrator account and the revoke control instead.
6. **Expect**: the same account-gone handling.

## Notes for whoever writes the actual tests

- Scenario 3 step 3 needs a way to submit a `PATCH` against one's own account outside the browser UI,
  since the control is never rendered there — a Rails controller test (`ActionDispatch::IntegrationTest`)
  is the natural fit, matching how 015's own "a non-administrator cannot grant rights to themselves"
  case is already tested at the controller level rather than the system level.
- `grace` (granted, not bootstrap) is deliberately used as the revoke target in Scenario 2, mirroring
  015's own test fixture choice ("everything below is asserted with her rather than with the bootstrap
  administrator, because the whole question is whether anything in the site distinguishes the two") —
  the same reasoning applies here: revoke must work identically regardless of how the target became an
  administrator.
